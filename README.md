# 午间热饭

一个仅供个人使用、面向 **iOS 17+ iPhone Safari / 添加到主屏幕**的纯静态 PWA。提前选菜，根据本地历史倒推下单时刻；用户把提醒导入系统日历，到点后自己进入官方外卖 App 核对并付款。

没有服务端、数据库服务、账号、统计、广告、云接口或外部图片。这里的 IndexedDB 是手机浏览器内置的本地存储。应用不会接入、登录、抓取或自动操作美团、饿了么、微信支付和支付宝。

## 本地运行

需要 Node.js 22.12+（或 24+）及 npm。

```bash
npm ci
npm run dev
```

打开终端显示的本机地址（默认 `http://127.0.0.1:5173`）。开发模式用于编辑，**不注册 Service Worker**，避免调试时被旧资源影响。

生产构建和离线验收：

```bash
npm test
npm run build
npm run preview
```

打开 `http://127.0.0.1:4173`，联网等待一次资源缓存完成，在「设置」确认已缓存，然后可断网刷新。`dist/` 是完整的静态站点，可由任何支持 HTTPS 的静态服务器托管。构建自动生成 `dist/sw.js`，预缓存实际打包出的全部应用资源。

手机访问电脑的普通局域网 HTTP 地址不满足 PWA 的安全上下文要求。请使用下述 HTTPS 部署地址验收真实 iPhone；电脑的 localhost 例外只适用于电脑自身。

## 免费部署到 GitHub Pages

本项目不要求注册任何付费服务，也不需要 Apple 开发者账号。

1. 在自己的 GitHub 账号下创建公开仓库，例如 `wujian-refan`。
2. 把本工作区的项目源码提交到仓库 `main` 分支。包含 `package-lock.json`，不要提交 `node_modules`、`work`、`outputs`、本地备份、日历文件或浏览器资料。
3. 在仓库的 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。
4. 推送 `main`，或到 **Actions → Deploy static PWA to GitHub Pages → Run workflow** 手动运行。
5. 工作流先执行 `npm ci`、单元测试和生产构建，再发布 `dist/`。成功后从部署结果打开 `https://你的用户名.github.io/wujian-refan/`。
6. 若使用其他默认分支，修改 `.github/workflows/deploy.yml` 的分支名。

Vite 的 `base: './'`、Manifest 的相对作用域和 Service Worker 的路径均支持仓库子路径，也可发布到域名根目录。不会把本地菜单、计划和历史纳入构建或部署；它们由运行中的浏览器存储。静态托管平台会收到普通静态资源请求及其基础访问日志，本应用不发送本地业务数据。

不要把导出的 JSON、ICS 或任何真实菜单写进仓库。`.gitignore` 已忽略工作目录和本应用默认命名的备份文件，但仍请在提交前检查文件列表。

## iPhone 添加到主屏幕

1. 使用 iOS 17+ 的 **Safari** 打开部署后的 HTTPS 网址。
2. 点击 Safari「分享」（方框向上箭头）。
3. 选择「添加到主屏幕」，保留名称「午间热饭」，点击「添加」。
4. 从主屏幕图标启动应用，在联网时等待一次缓存完成；「设置」中能看到资源是否准备好。
5. 建议在这个主屏幕应用内建立正式数据。若从 Safari 窗口迁移后没有看到数据，在原窗口导出 JSON，再从主屏幕应用导入。

不依赖安装弹窗；iPhone 手动使用 Safari 分享菜单安装。首次离线前必须至少完整加载一次生产版。浏览器可能因用户清理、低存储等原因移除本地数据；「请求保留本地存储」是否允许由浏览器决定，**定期 JSON 备份仍然必要**。

## 三分钟开始

1. 「今天」→「安排第一顿午餐」，一次填好店铺名、第一份套餐及菜品；默认耗时 35 分钟、余量 5 分钟，保存。
2. 紧接着选择今天或明天的开饭时间、最晚送达时间，确认主套餐并保存。已有店铺后，每天只需这一步。
3. 在计划卡片点击「添加下单提醒」，下载或分享 ICS 文件，并在系统日历中确认添加。

不要把演示商家当成真实数据：初次启动为空，本项目不内置任何用户菜单、计划或历史。未保存店铺链接时，按钮会提示在官方 App 搜索；已保存时优先直接打开用户填写的 http/https 分享链接。不读取链接内容，不探测是否安装外卖 App，也不尝试绕过平台的打开方式。

## 日历提醒：生成、导入、确认

### 应用内的操作

1. 打开计划卡片的「添加下单提醒」。
2. 点击「下载 ICS 文件」，或「分享 / 打开日历文件」调出支持文件分享的系统面板。
3. 当 iOS 出现日历的事件添加界面时，检查事件标题 `该点外卖了：{店铺名}`、日期与时间，选择自己的日历并确认添加。
4. **一定回到系统日历找到该事件，确认提醒为「事件发生时」。** 文件已下载、分享成功、页面显示「已生成」均不能证明已经添加日历。
5. 首次使用时，在 iPhone **设置 → 通知 → 日历**（不同 iOS 版本也可能在 **设置 → App → 日历 → 通知**）允许通知；同时检查声音、锁定屏幕以及专注模式等系统设置。
6. 到点后打开主屏幕「午间热饭」，首页优先展示今天最近的有效计划。点击保存的店铺入口，自行确认实时价格、优惠、配送时段和地址并付款。

网页不读取或申请系统日历写入权限，不会在后台准点自行通知。倒计时只在网页打开时刷新；没有 Notification API、Web Push、后台下单任务或模拟系统通知。

### 如果 Safari /「文件」只出现预览，没有添加入口

iOS 版本、打开来源及共享目标不同，本地 Blob/下载的 ICS **不能保证直接出现「添加到日历」按钮**，主屏幕模式也不保证会有这个入口。应用不会假称已完成导入。

不上传私人数据的可用兜底：

- 在提醒窗口展开「只有文件预览，没有『添加』按钮？」→「复制完整提醒信息」，到系统日历点 `+`，标题填 `该点外卖了：店铺名`，开始时刻填应用显示的**日期、时区与建议下单时间**，粘贴说明，并设提醒为「事件发生时」，最后点「添加」。这是手动建立相同的系统提醒，不是假装成功导入 ICS。
- 如有自己的 Mac，可用 AirDrop 传送 ICS 后，在 Mac 的「日历 → 文件 → 导入」中打开，选择自己的日历。**仅当用户自己已有并启用了日历账户同步时**，事件才会同步到 iPhone；不要为了本应用强制开通云同步。

Apple 文档明确列出从 Mail 导入 ICS，但这会让用户主动把导出文件交给邮件服务，**不是本项目默认流程，也不是本地隐私兜底**。本项目不发送邮件、上传文件、生成公开私人日历 URL 或调用任何日历云接口。不能用静态服务端去托管含私人计划的订阅地址。

ICS 使用 RFC 5545：UTF-8、CRLF、最多 75 字节折行、文本转义、UTC DTSTART、VEVENT 和即时 `VALARM`（`ACTION:DISPLAY`、`TRIGGER;RELATED=START:PT0S`）。描述包含套餐、菜品规格、备注、预算、吃饭/最晚送达时间、时区和店铺链接。无邀请收件人或组织者，不会发出邀请邮件。

### 修改、换餐、延后、取消

应用不能更新或删除系统日历事件。修改已生成提醒的计划后，页面会明确提示**删除旧事件并重新生成**；新版本使用不同 UID。重复导入同一文件的结果也由日历客户端决定，请避免重复添加。

- 编辑计划、换备选餐：按当前有效历史重新预测。编辑可调整安全余量；换餐保留本次手动余量。
- 「延后 5 分钟」：从原建议时刻与当前时刻中较晚的一个再延后 5 分钟，仅改应用内下单时刻；若预计送达已超过最晚时间，则阻止并提示编辑或换餐。
- 修改店铺/套餐：相关计划会标记日历内容变更；保存的预测耗时不被静默改写。
- 「我已自行下单」：只标记本地状态，不操作外卖平台。需要时可稍后记录真实下单和送达时间。
- 「今天不点了」、删除计划/店铺/套餐：日历中的旧事件仍需自己删除。删除店铺/套餐时会先说明关联数据范围并要求确认。

## 预测和时间规则

```text
建议下单时刻 = 希望吃饭的真实时刻 − 预测履约分钟数 − 安全余量分钟数
```

- 每家店按餐段分开。根据实际送达的本地时刻分类：早餐 05:00–09:59、午餐 10:00–15:59、晚餐 16:00–21:59、夜宵为其余时间。
- 使用**同一店铺、同一餐段，按实际送达时间倒序的最近 8 条有效记录**的中位数。偶数条取中间两个数的平均值，保留半分钟等精度。有效样本不足 3 条时使用店铺默认值。
- 履约耗时必须大于 0 且不超过 360 分钟。记录时可主动取消「参与预测」；异常备注不会自动排除样本，避免凭关键词猜测。
- 「手动重置预测」保留历史，只使用重置时刻之后送达的有效记录；不足 3 条时回退默认。店铺默认值、手动安全余量和已有计划均不自动改写。
- 计划保存当时的预测数值与依据。新的历史影响下一次创建、编辑或换餐，已有日历提醒不会静默漂移。
- 每份计划保存创建时的 IANA 时区与 UTC 真实时刻，旅行换时区后仍显示原计划时区；最晚送达日期可显式选为次日。
- 使用打包进应用的 Temporal polyfill，不要求 iOS 17 原生支持 Temporal。按真实经过分钟倒推，不使用固定 24 小时或字符串时间减法；支持跨日、跨月和闰年。
- 夏令时跳变产生的不存在/重复的墙上时间会被拒绝，并要求换一个明确时刻，避免擅自选早一小时或晚一小时。由明确时刻向前倒推跨越 DST 则正确计算。
- 过最晚送达时刻的计划标为过期，不再作为有效待下单计划；建议下单时刻已过但尚未超过最晚送达时刻时，提示现在自行核对。不会为过去的时刻生成提醒。

## 本地数据与导入导出

「设置 → 导出 JSON」生成版本化完整备份，仅包含本地店铺、套餐、计划和历史，外加格式名、版本号和导出时间。少量界面偏好（默认午餐时间、默认余量）仅放在 LocalStorage，不包含在备份内。

导入流程：先选文件并检查格式，再显示店铺/套餐/计划/历史数量，选择：

- **合并**：同 ID 以备份为准，无冲突数据保留。之后再次校验整体引用关系，冲突若导致关联不一致会拒绝，不会部分保存。
- **覆盖**：替换全部业务数据，另有确认步骤；不改系统日历。

校验包括最大 10 MB、版本、严格字段、数字范围、文本长度、重复 ID、链接协议、时区/日期顺序、关联店铺/套餐/历史、主备选不重复、日历版本等。无效文件不会破坏当前数据。写入使用单个 IndexedDB 读写事务，完成后才提示成功。读取或写入失败提供中文错误，不自动丢弃原数据。

「清空全部本地数据」需要先输入“清空”，再进行最终确认，删除业务数据和界面偏好。应用缓存只是静态代码资源，不含业务数据；清空不卸载主屏图标或替你删除日历事件。建议只在一个应用窗口内编辑，避免多窗口同时更改。

不收集详细地址；备注仅建议使用“学校办公室”等简短非敏感标签。实际配送地址一律在官方 App 核对。应用无法约束用户自己在自由文字、导出文件或系统分享目标中选择的内容，请不要输入账号、验证码、Cookie、支付信息等敏感内容。若用户主动把导出文件放进云盘，或把日历事件加进 iCloud 等账户，其后续同步由用户选择的系统服务负责，PWA 本身不上传。

## 项目结构

```text
src/domain.ts          类型、严格备份校验、时间计算、预测、合并
src/storage.ts         IndexedDB 原子读写、少量 LocalStorage 偏好
src/ics.ts             ICS 转义、折行、事件/提醒生成与本地下载
src/forms.tsx          店铺、套餐、计划、收餐表单
src/App.tsx            今天 / 计划 / 店铺与套餐 / 历史与预测 / 设置
src/components.tsx     内置 SVG 图标、对话框及通用界面
src/styles.css         暖色响应式样式、单手底部导航、safe-area
public/                Manifest、内置图标（不依赖远程图片）
scripts/build-sw.mjs   构建后按真实资源列表生成离线 Service Worker
.github/workflows/     GitHub Pages 测试、构建、免费部署工作流
```

Service Worker 只拦截自身作用域内的静态应用请求，不拦截外卖链接、不缓存私人导出文件、不发送业务数据。新版本等待旧窗口关闭再接管，避免中途混用两版资源；更新后关闭全部该站点窗口 / 主屏应用再打开即可。

## 测试与真实设备验收

```bash
npm test                 # Vitest：时间、预测、ICS、备份、IndexedDB
npm run build            # TypeScript 检查、静态构建、离线资源生成
```

ICS 使用独立 `ical.js` 解析器交叉校验，不仅检查字符串。IndexedDB 测试使用 `fake-indexeddb` 验证完整往返和无效写入后原数据保持。

浏览器回归脚本：

```bash
npx playwright install webkit
npm run build
npm run preview
# 另一个终端：
npm run test:browser
```

浏览器脚本只使用测试用的隔离浏览器上下文，检查 390px 布局、建立店铺/套餐/计划、导出 ICS、编辑后的旧日历提示、JSON 导出/导入、离线重新打开与编辑。它不会接触你的 Safari 资料。还覆盖跨店备选换餐、保持手动余量、历史中位数校准、重置、店铺排序和关联删除。截图和中间文件写入已忽略的 `work/`。可用 `BROWSER=chromium npm run test:browser` 运行 Chromium（macOS 优先使用已安装的 Chrome；其他环境先安装 Playwright Chromium）。

桌面 WebKit 模拟不能证明真实 iPhone 的主屏安装、系统分享入口、Apple 日历导入按钮或系统通知实际响铃。正式使用前请在自己的 iPhone 上做一次完整检查：

1. 从 HTTPS 安装主屏图标，建立测试套餐并创建未来 5–10 分钟的下单提醒。
2. 将 ICS 导入系统日历；若无添加入口，按上述本地兜底手动新建，核对标题、说明和即时提醒。
3. 关闭应用、锁屏，确认系统日历在设定时刻提醒。
4. 从主屏打开应用，确认今天的最近计划、链接和复制清单正常。
5. 飞行模式重开、编辑备注、关闭再打开，确认数据保留。
6. 用 JSON 备份完成一次导出、清空（双重确认）与恢复；检查旧日历事件是否需删除。

## 规范与平台参考

- [Temporal ZonedDateTime 文档](https://tc39.es/proposal-temporal/docs/zoneddatetime.html)：时区、夏令时与 disambiguation。

- [Apple：iPhone 多个日历设置](https://support.apple.com/en-gb/guide/iphone/iph3d1110d4/ios)：选择和管理系统日历。
